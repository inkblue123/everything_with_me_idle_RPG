# ADR-0001：挖矿复用现有实现，只补内容层

- 日期：2026-10-23
- 状态：已接受
- 相关：`docs/plan/mining.md`

## 背景

准备"开发挖矿系统"时，调研发现它并不是空白：`js/GameRun/live_plan/Explore_collection/mining.js` 已有 933 行
`Mining_manage`（6 个状态机 + 矿石目标对象 + 掉落结算），界面、4 种矿层数据、地点挂矿、定时复活、
事件解锁全部就位，并已接入主循环与存档。真正的缺口是内容层：没有镐子、挖矿不加经验、洞内没有地图数据、
矿石没有下游配方。

于是有两条路：按 `idea5` 的设计重写一套，或者在现有实现上补内容。

## 决策

**复用现有实现，只补内容层**；不重写状态机，不改伤害/掉落公式。

## 理由

1. 现有实现与 `idea5` 的公式一致（挖矿力 − 防御 → 生命归零 → 按稀有度给掉落），重写不会带来设计收益。
2. 重写要重接四处既有接线：主循环派发（`live_plan_manage.js:181`）、存档读档（`:67/:112`）、
   界面 tab（`Live_plan.js:111-319`）、定时复活（`run_manage.js:131`）。每处都是回归风险，且无用户可感知的改善。
3. 挖矿的"不完整"表现为玩家体验层（没镐子、没成长、洞里没图），不是架构层。

## 后果

- 接受现有 6 状态机的约束：本计划不做"挖得越快档位越高""找矿按钮""稀有度可视化"这类机制改造。
- 若将来要做时间档位（照伐木的 `reward_level_time`），需要另开一次改造，而不是在本计划里顺手加。
- 现有 `Mining_manage` 里已知的两处瑕疵（`live_plan_flag[0]` 位序、界面空壳控件）在 M4 一并修，不构成重写理由。
