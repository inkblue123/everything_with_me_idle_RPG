## 1. 领域词汇表（本次会话固化的统一术语）

| 词                                  | 含义                                                                                                                         | 备注                                                                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| buff                                | 施加在目标身上、随时间/回合生效的效果集合                                                                                    | 现有                                                                                                                       |
| 时间型 buff / 回合型 buff           | 以游戏时间为准 / 以玩家战斗回合为准计时                                                                                      | idea3 问题 5 要求分开展示                                                                                                  |
| time_type                           | buff 的计时依据类型                                                                                                          | 现只有 `game_time_buff` 真跑；`combat_round_buff`/`combat_active_buff` 为空壳                                              |

| 分类 buff_tag                       | 正面 / 负面                                                                                                                  | idea3 问题 6 定：**只做这两类**，中立标签暂不做                                                                            |

| 钩子 hook                           | 在"攻击时/受击时/施法时/击杀时…"通知 buff 系统的接口                                                                         | 本稿**只定接口，不加调用点**（见 §4.4）                                                                                    |

## 2. 现状快照（2026-09-11 核对）

### 2.1 数据层

-   `js/Data/Buff/Buff_class.js`：的 `Buff` 只有 `id / name / desc / buff_value[]`；`time_type`/`time_value` 不写在构造器，只能由 `set_time_type()` 写入（未调用则为 `undefined`）。`add_buff_value(buff_type, data_type, data_value)` 追加**固定三元组**。
-   `js/Data/Buff/Buff_normal.js`：**8 个 buff、37 条效果行**（测试 3 个 + 睡眠/起床 + 疲劳/极度疲劳/精力充沛）。**全部是 `game_time_buff`**，无任何回合型条目。DB 实际出现的 `buff_type` 只有 3 种（`continuous_start_no_restore` / `continuous_start_restore` / `only_start_restore`）。
-   `js/Data/Enum/Enum_buff.js`：**6 条 data_type 通道**——`bool_data_type`(`GS_rest_flag`)、`change_data_attr_data_type`(4 项)、`updata_end_attr_data_type`(13 项)、`global_set_flag_data_type`(`GS_rest_flag`)、`set_game_speed_num_data_type`(`change_game_speed`)、`set_game_speed_ratio_data_type`(**空**)。**通道白名单里没有任何抵抗相关项**。

### 2.2 运行层

-   `Player_buff.js` 的 `BUFF` 基类：深拷贝 DB 内容，并按效果类型补 `start_flag` / `start_data` 两个运行时记账字段。
-   `game_time_BUFF`：100ms tick，按"每秒数值 × 经过时间比例"算增量；`delete_buff` 对 restore 型取负返还。
-   `Player_Buff_Manage`：容器 `game_time_buff` / `combat_round_buff`；汇总 `end_buff_attr` → `end_data_attr`；帧入口 `run_player_buff()` **只跑 `game_time_buff`**；`restart_end_buff` 按 `Enum_buff` 的通道分派。
-   **`combat_round_buff` 是空壳**：只有容器、清空循环、显示位；`combat_active_buff` 全仓只有 `get_continuous_start_data` 里一个分支，**无类、无条目、无存档、无计时推进**。
-   存档 `save_Player_Buff_attr()` **只存 `game_time_buff`**，且存整个对象；`load_init` 只恢复 `buff_have_time` 与 `start_flag`/`start_data`，**不恢复自定义时长/数值**（因为现在也没有自定义值）。

### 2.3 施加方（谁在用）

全仓 `set_buff_attr`/`delete_buff_attr` 共 13 处有效调用，全部来自：地点进出（场地 buff）、迷你事件、精力阈值（疲劳/精力充沛）、测试按钮。
**战斗、技能、消耗品三处一个都没接**。

### 2.4 与本次相关的其他现状

-   **抵抗力无消费点**：`resistance_point` 基础值 10，`true_resistance_point` 已算出，但只在 UI 展示；战斗受击结算只用 `true_defense`。
-   **战斗/技能无 buff 钩子**：`combat_manage.js` 的攻击/受击/击杀时刻只有硬编码 `record_*`/`set_game_log`；`Player_active_skills.js` 里**留着一行空注释"处理玩家 buff 里的额外效果"**，位置在、代码无。
-   **消耗品侧已接好形状**：`consumable_manage.js` 的 `get_consumable_use_data` 已识别 `get_buff` 但**只打日志不生效**；`Function.js` 的 `get_merge_use_attr` 已实现"`get_attr` 按 attr_id 相加、其他类型原样透传"；实例 `ex_data = {seasoning, bonus}` 已能产出、参与背包 key 哈希、并存档。

## 3. 目标 / 范围 / 非目标

**目标**

1. 给 buff 数据库加上"够表达分类/层数/系列/等级/作用域/时间规则/效果通道"的**必需字段**。
2. 把"获得一个 buff 时发生什么"做成**规则引擎**（现在是"同 id 无脑替换"）。
3. 立起**六类效果通道**的划分（这是"新 buff 装不下"的根因）。
4. 立起**对外接口**（施加/移除/查询/钩子），并**接通消耗品 → buff**。
5. 运行层**目标抽象**（玩家/敌人通用）。

**范围**：以上全部落在 `js/Data/Buff/`、`js/Player/Player_buff.js`、`js/Data/Enum/Enum_buff.js`、必要的战斗/技能/消耗品对接点。

**非目标（本稿明确不做）**

-   具体 buff 数值内容（各系列条目与数值）——**只作参考素材**。
-   生活类 buff（菜品/调味/药浴永久 buff 等）的**具体设计**——本稿**只留接口**（§7），归属与数值以后再说。
-   战斗侧加 hook 调用点——**只定接口**（§4.4）。

## 4. 框架设计（四大块）

### 4.1 数据结构（只加必需字段）

在现有 `id / name / desc / time_type / time_value / buff_value[]` 之外，**只加以下必需字段**（其余如 `resistable`/`cleanable`/`show_flag`/`target_type` **以后用到再补**）：

| 字段                      | 取值示例                                                                                                                    | 用途                                                 |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `buff_tag`                | `positive` / `negative`                                                                                                     | 正负面分类（净化/增益类技能要按此筛选）              |
| `stackable` + `max_stack` | `true` / `10`                                                                                                               | 可叠层与层数上限                                     |
| `series` + `series_level` | `'fire'` / `2`                                                                                                              | 系列与系列等级（覆盖判定、按系列查询）               |
| `series_cover_rule`       | `'cover_lower'`（无脑覆盖）                                                                                                 | 同系列互相顶替的规则（运行逻辑要用，故随系列一起加） |
| 层数时间规则              | `refresh` / `no_refresh`、`layer_decay`（每层 ×0.75）、`end_reduce_layer`（结束减 1 层）、`trigger_clear_layer`（触发清层） | "重复获得时发生什么"                                 |
| `buff_level`              | `1..5`                                                                                                                      | 抵抗力判定用（与 series_level 分开）                 |
| `scope`                   | `normal` / `combat` / `life`                                                                                                | 作用域                                               |
| `effect_type`             | 六类之一（§4.3）                                                                                                            | 决定效果走哪条通道                                   |

**同时**：`buff_value` 的三元组需能携带**通用配置对象**（如 `effect_config`），以容纳 DoT 公式、事件条件、记录比例等——因为把一个公式塞进 `data_value` 单个数字里表达不了。三元组保持向后兼容（老 buff 不填即默认）。

### 4.2 运行逻辑

1. **获得规则引擎**（旧稿"改动 3"，本框架最核心）：把"得到一个 buff"拆成顺序流程——
   ① 抵抗力判定（§4.2-5）→ ② 净化抵消（若将来做，拦截点在此）→ ③ 系列覆盖判定（`series_cover_rule`）→ ④ 同类获得规则（`stackable` 叠层 / `refresh` 刷新 / `no_refresh + end_reduce_layer` 加层不动时间 / `trigger_clear_layer`）→ ⑤ 免疫/抗性检查 → ⑥ 构建对象、init、入容器。
   未来几乎所有 buff 的差异都体现在"重复获得时发生什么"，所以这一步是骨架。
2. **层数**：运行对象增加 `stack`、`max_stack`、`series`/`series_level`；`buff_have_time` 不再是 init 时定死，需支持"每多一层时长衰减（获得时重算）""结束减 1 层并重启计时""触发后清层""达阈值引爆"。
3. **时间体系（三型全纳入）**：
    - `game_time_buff`：现有，保持；
    - `combat_round_buff`：**真做**（以玩家战斗回合为计时单位；回合定义见 §10 附录 B）；
    - `combat_active_buff`：补齐类与构建路径（或明确搁置，但不再让 `set_buff_attr` 崩）。
4. **作用域 + 战斗外加速消失**：每帧按当前是否战斗决定哪些 buff 生效；**退出战斗时**（挂到 `change_GS_game_statu` 的 combat 分支）：正面战斗 buff 停止生效/清除，负面战斗 buff 进入加速消失（时间型每秒扣 5 秒、回合型每秒结算 1 回合）。
5. **抵抗力判定**（纳入框架）：debuff 带 `buff_level`；抵抗力每 100 点一阶段；低于抵抗力等级 → 免疫，同级 → 持续时间按阶段内数值缩短，高于 → 直接获得。**数值策略后续再调**（见 §9）。
6. **目标抽象**（纳入框架）：把 `BUFF` 运行类从"玩家属性"解耦成**目标无关**（伤害/效果统一走目标接口），玩家与敌人各自实现适配层。敌人侧需要：buff 容器、结算循环、DoT 与死亡判定、图标位。
7. **汇总机制**：**增量 + 按需全量重算（混合）**。保留现有"每帧增量加减"，但在**层数变化 / 转化 / 净化 / 系列覆盖**这类"整条贡献被改写"的时刻，**从所有存活 buff 重新累加** `end_buff_attr`（避免增量累积浮点误差）。

### 4.3 效果通道（六类，框架核心）

| 通道 effect_type    | 含义                                                                    | 落地方式                                                  | 依赖             |
| ------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- | ---------------- |
| `attr` 属性         | 数值加/减算进属性或资源                                                 | 走现有 `end_buff_attr` 总对象                             | 现成             |
| `dot` 持续伤害      | 每秒/每层对目标结算伤害（固定值/当前生命%/最大生命%/施术者攻击力比例…） | 新结算入口；打玩家走 `change_data_attr`，打敌人需目标接口 | 目标抽象         |
| `event` 事件触发    | 在"攻击时/受击时/施法时/移动时/击杀时"触发                              | 由**钩子接口**驱动                                        | 钩子（只定接口） |
| `behavior` 行为修改 | 攻速延长、技能失败概率、锁目标、无法行动等"结算时查询"型                | 战斗系统提供读取点（buff 不主动改属性）                   | 战斗侧读取点     |
| `record` 延迟结算   | 运行中记录、结束时/达阈值一次性结算                                     | 运行对象记录字段 + 专门结算入口                           | 运行对象         |
| `transform` 转化    | 把正面 buff 转成 debuff、结束时转化、跨 buff 操作                       | 管理类提供"查询+替换+新增"的**原子接口**                  | 管理类 API       |

### 4.4 对外接口

-   **施加**：`set_buff_attr(id)`（现有，只收 id）+ **【改动 11】传参版**——允许施加时覆盖 `time_value` / `data_value`（见 §7 与 §6 ADR-4）。
-   **移除**：`delete_buff_attr(id)`、`reset_buff_attr()`（现有）。
-   **查询（只列必需）**：按 id 增删查、**按系列查**（`has_series` / `get_series_buffs`）、**按等级查**（`get_buff_level`）。其余（按正负面枚举、按 effect_type 枚举、批量叠层、拒收/拦截）**列为后续**。
-   **钩子（只定接口，不加调用点）**：定义钩子清单（`on_attack` / `on_attacked` / `on_cast` / `on_move` / `on_kill` / `on_crit`…）与统一入口（如 `P_buff.trigger(name, ctx)`），**本次不在战斗/技能代码里加调用**——等具体 event 类 buff 落地时再接。

## 5. 改动清单（保留旧稿 1–10 骨架 + 新增 11）

> 各项格式：**位置 / 现状 / 要改什么 / 依赖**。行号见附录 B（会过期）。
> **⚠️ 标记说明（2026-09-14 加）**：`【本期实现】` = 本期（燃烧测试切片）真的做；`【本期实现（部分/极简版）】` = 只做其中一小块；`【设计预留】` = 本期**不实现**，只把接口/字段位置写进计划。本期总范围见 ADR-18 与 §13。

1. **【本期实现（部分）】数据库结构扩展**（`Buff_class.js` / `Buff_normal.js`）：加 §4.1 的必需字段；`buff_value` 支持通用配置对象。→ 依赖：无（地基）。**本期只加 `stackable`（可叠层标记）。**
2. **【本期实现（部分）】运行对象加层数与运行时状态**（`Player_buff.js` 的 `BUFF`）：加 `stack`/`max_stack`/`series`/`series_level`；加记录型字段（`record_data`/`countdown`）；加施加者信息（`caster_id`/`caster_attack`/`kill_num`，目标抽象需要）；`buff_have_time` 改为可按层数规则重算。→ 依赖：1。**本期只加 `stack`。**
3. **【本期实现（极简版）】获得规则引擎（重构 `set_buff_attr`）**：按 §4.2-1 的流程；补齐 `time_type` 分支不再崩。→ 依赖：1、2。**本期只做「已有同 id → `stack` +1 且刷新剩余时间」这一条分支；抵抗力/净化/系列覆盖三步全部留空。**
4. **【设计预留】效果通道扩展**（`updata_end_buff_attr` / `restart_end_buff` / `Enum_buff.js`）：按 §4.3 六类分流——`attr` 走现有通道，其余五类开新入口/新枚举登记。→ 依赖：1（`effect_type`）。**本期掉血走现有 `continuous_start_no_restore` + `health_point` 通道，一行新通道都不用开。**

## 7. 已定决策记录（ADR）

-   **ADR-1【设计预留】效果通道定为六类**（attr / dot / event / behavior / record / transform）。
    背景：现有通道只能表达"数字增量 → 属性"，DoT、事件、行为、延迟、转化五类根本装不下，这是新 buff 落不了地的根因。
    决策：把 `effect_type` 作为一级分类，六类各走各自入口。理由：分类清晰，未来 buff 只需声明走哪条通道。后果：需新开 5 条入口，且 dot/event/transform 依赖目标抽象与钩子（因此改动 4 与 5 要一起做）。
-   **ADR-2【设计预留】汇总机制用"增量 + 按需全量重算"混合**。
    背景：现为纯增量加减，层数变化/转化/净化会频繁改写整条贡献，易累积误差。
    决策：日常仍增量；在贡献被整条改写的时刻从所有存活 buff 重新累加。理由：兼顾性能与正确性。后果：需明确"哪些时刻触发全量重算"（层数变化、转化、净化、系列覆盖、buff 增删）。
    **【2026-09-20 补充点名】已有一个具体需求在等它**：属性类叠层 buff 需要"层数 = 属性"的稳态语义（如冰系列「每层防御 −5%，层数变了属性立刻跟着变」）。没有全量重算，`tick` 行只会一直累加、`on_apply` 行加层不重算，两者都表达不了。详见 §9 的「属性类叠层 buff 缺"层数 = 属性"的稳态语义」。
-   **ADR-3【设计预留】运行层做目标抽象（玩家/敌人通用）**。
    背景：buff 现在是玩家专属，敌人无 buff 容器；DoT/传播/敌人给玩家上 debuff 全都需要双方。
    决策：`BUFF` 运行逻辑与玩家属性解耦，玩家/敌人各实现目标适配层。理由：一次做对，避免日后大改。后果：改动面扩大（敌人侧容器/循环/图标/死亡判定），且需施加者信息。
    **【2026-09-22 补充】落地规划见 §15**：已查明"玩家绑定面只有 5 个模块级函数"，并定了"敌人也建派生属性层、适配层写进 `place_enemy`"。
-   **ADR-4【设计预留】消耗品施加 buff 采用"施加时传参"（改动 11 取 B）**。
    背景：`set_buff_attr(id)` 只收 id，时长/数值全读 DB；而菜品/调味的加成天然是"这一次具体是多少"。
    决策：允许施加时覆盖 `time_value`/`data_value`。理由：否则"每次数值不同"只能靠预设海量固定 buff 或干脆不走 buff。后果：连带改四处——运行对象保存自定义值、**存档保存自定义值**、展示显示实际值、明确"同 id 但数值不同"的替换/叠层规则（现为"同 id 新替换旧"）。
-   **ADR-5【设计预留】数据字段只加必需项**。
    背景：旧稿列了 14 个候选字段，其中不少现在用不到。
    决策：先加 §4.1 的必需字段，`resistable`/`cleanable`/`show_flag`/`target_type` 等用到再补。理由：避免为不在视野内的需求设计。后果：将来加字段需回头改 DB 结构与校验。
-   **ADR-6【设计预留】生活类 buff 只留接口、不入范围**。
    背景：菜品/调味/药浴永久 buff 与本次框架相关但不是本次目标。
    决策：本稿只在 §7 定义接口，不设计其内容与归属。理由：先把框架立起来。后果：菜品"每秒恢复"暂时无法真正生效（继续走占位）。
-   **ADR-7【设计预留】系列覆盖只清「系列等级严格更低」的，同级与同 id 走叠层**（2026-09-14 追加，修正 idea3 问题 6）。
    背景：idea3 问题 6 定「无脑全部覆盖」（`idea3.md` L222-223：只要有一个 2 级火系列 buff，1 级的所有可叠层不可叠层正面负面全部清除且不可获得），而 §4.2-1 的流程顺序是「③ 系列覆盖判定 → ④ 同类获得规则（叠层/刷新）」。若 ③ 按字面执行，同 id 也满足「同系列」条件，旧实例会被清掉再加新的，**层数永远停在 1，叠层机制直接失效**。
    决策：覆盖判定只在「同系列**且**系列等级严格更低」时触发；系列等级相同（含同 id 重复获得）不覆盖，落到 ④ 的叠层/刷新规则。
    理由：`idea4.md` L102 / L251 火/冰系列原文即为「高级覆盖低级、同级 buff 可以共存」，毒系列 L170 为「该系列的 buff 可以共存」，按等级判定才能与这三条同时成立。
    后果：「无脑全部覆盖」的简化实现被否，覆盖判定必须知道对方的系列等级；判定顺序固定为「同 id → 叠层 / 同系列低级 → 覆盖 / 同系列同级 → 共存」。
-   **ADR-8【本期实现】层的计时模型：单实例 + stack 数字 + 单计时器**（2026-09-14）。
    背景：曾设想「每层独立计时」（每层各自有剩余时间）。若采用，容器须从 `id → 对象` 改为 `id → 列表`，连带记账 key（`Player_buff.js` L424 `buff_type + '_' + buff_id`）、存档 key（L244 `[id]`）、界面 `div_id`（L583 `buffid_ + id`）、排序 `buff_id_sort`（L537）四处结构重做，并波及现有 8 条 buff 的全部读写路径。
    决策：一个 buff 实例不论多少层，只保留一个生效时间；加层时按层数规则重算它（火系列「每多一层 ×0.75 / ×0.5」即获得时重算一次），到期时「减 1 层并重启计时」，减到 0 才删除。
    理由：`idea3.md` L134 已明确「多复杂的 buff，它的生效时间是对整个 buff 而言的，不应该设计同一个 buff 有几个生效时间」；三个 idea 文件里唯一出现「每层独立计时」的是 `idea4.md` L198 的瘴气**格子区域**，而区域不挂在单位身上。旧稿也只在字段层加 `stack`，未改容器。
    后果：容器与四处 id-key 结构保持原样，改动集中在 `Player_buff.js`；需要新增「减层」这条现有代码完全没有的路径（现在只有「整条删除 + 取负返还」）；代价是「5 层毒各自陆续到期」这种表现做不了，毒系的「结束减 1 层」表现为每 10 秒掉 1 层。
-   **ADR-9【设计预留】叠层型 buff 必须支持非累加效果**（2026-09-14）。
    背景：现有骨架（`end_buff_attr` 累加 + `restart_end_buff` 差值分发）预设「所有效果都能变成可累加数字」，`Player_buff.js` L406-409 对非 number 的数据直接跳过并告警。而 `idea4` 的叠层型 debuff 中大量效果不可累加：中毒「每秒每层受到当前生命值 0.1% 的伤害」（L173）、心猿意马「施放主动技能时每层 1% 概率失败」（L463）、血咒「记录 20% 伤害、结束时一次性释放」（L482）、魔气侵蚀「把目标身上的正面 buff 转化为 debuff」（L517）。
    决策：叠层型 buff 的效果范围**包含非累加效果**，因此必须新增一条「到点执行动作」的结算管线，与现有累加管线并行，即 §4.3 的 dot / event / record / transform 四条通道。
    理由：只做可累加数字虽然改动最小，但会让 idea4 的毒 / 心魔 / 煞气 / 咒印系列根本无法落地，等于本次升级的主要目标落空。
    后果：工作量与风险显著上升（新增结算管线 + 目标接口）；**与本稿 §4.4「钩子只定接口、不加调用点」直接冲突**——触发型效果（攻击时 1%、受击时记录）在不加调用点的情况下无法生效，该条约束必须重议；「累加 vs 动作」成为框架里真正的分水岭，而「有没有层数」不是。
-   **ADR-10【设计预留】效果通道挂在「效果行」上，一个 buff 可混多通道**（2026-09-14）。
    背景：本稿 §4.1 把 `effect_type` 列为 buff 级必需字段，§4.3 却把它描述成「效果怎么落地的一级分类」，两处矛盾。而现有 `buff_value` 三元组本来就是效果行，DB 里的条目已经混类（`sleep_1` = `continuous_start_no_restore` + `only_start_restore`×2；`test_buff3` = `continuous_start_restore` + `only_start_restore`）；`idea4` 里玄冰（L272）、瘟疫之毒（L181）、煞气入体（L509）、妖气弥漫（L521）都是「每层 -X%（累加）+ 攻击时 Y% 概率（动作）」写在同一 buff 内。
    决策：`effect_type` 挂在**效果行**上，一个 buff 可同时含多条不同通道的效果行。
    理由：拆不开——把混类 buff 拆成同名的多个 buff，会撞上「容器以 id 为 key」（ADR-8），两个实例互相覆盖。
    后果：buff 级不再有唯一通道，§4.1 中「buff 级 `effect_type` 字段」作废，改为效果行字段；`add_buff_value(buff_type, data_type, data_value)` 三元组需扩展为可携带通道与配置对象。
-   **ADR-11【本期实现】周期型效果沿用 100ms 摊算，不另设整秒结算**（2026-09-14）。
    背景：`idea4` 的 DoT 大多写「每秒每层受到一次伤害」（中毒 L173、剧毒 L177、灼烧 L106 等）。若整秒结算，需 buff 实例自带一个秒计时器；而现有 continuous 型已经是 100ms 摊算（`Player_buff.js` L200 `data_value / 1000 * time_in`）。
    决策：周期型效果统一沿用 100ms 摊算，不为 DoT 另设整秒结算。
    理由：复用现有 tick 与算式，不新增时钟，实现面最小。
    后果：（1）「当前生命值 X%」「最大生命值 X%」类伤害因摊算而略偏小（复利效应），数值按摊算口径定；（2）**「每秒受到一次」实际变成「每 100ms 受到一次」**；为此 **2026-09-14 定案：DoT 不打游戏日志、不飘字，只改血量**（与现有 continuous 型一致），否则同时中三四种 DoT 时游戏日志会被每秒几十条刷爆；（3）阈值引爆、记录后一次性释放、结束时结算这类「时间点动作」不属于周期型，不适用本条，仍按各自的时间点触发。
-   **ADR-12【设计预留】玩家与敌人通用，但敌人身上的 buff 不进存档**（2026-09-14）。
    背景：DoT 与触发需要打到敌人，而敌人血量是裸字段（`combat_manage.js` L163-166 `enemys[i].health_point -= p_damage`），玩家走 `P_attr.change_data_attr`，两者口径不同；敌人实例 `place_enemy`（`enemy_manage.js` L10）离开战斗区时被整体丢弃（`delete_all_enemy` L420-434）；`place_enemy.save_init()`（L53-68）是逐字段挑着恢复，新增字段不会自动还原。
    决策：buff 运行逻辑做成玩家 / 敌人通用（目标抽象）；但敌人身上的 buff **不进存档**，离开战斗区或读档即清空。
    理由：敌人本来就在离开战斗区时整体丢弃，为其单独扩存档收益低；可省掉改动 9 的敌人侧部分。
    后果：在战斗中手动存档再读档，敌人身上的 debuff 会清空；`place_enemy` 需新增 buff 容器与结算调用点；**敌人因 DoT 死亡时无法复用 `enemy_death(enemy, main_Attack)`**（该函数需要一次攻击对象用于击杀记账），该路径需另行定义。
    **【2026-09-14 修订】敌人侧本期不做**，且不再假定「与玩家共用同一套运行逻辑」：敌人身上的 buff 将来在**运行敌人状态时单独处理**，可能另建一个专门的 buff 管理类。ADR-12 中「玩家与敌人通用」降级为**待评估的方案之一**，不再是既定决策。
-   **ADR-13【设计预留（已被 ADR-18 收窄）】只加玩家侧的钩子调用点（攻击 / 受击）**（2026-09-14）。
    背景：ADR-9 把触发型效果纳入范围，而本稿 §4.4 / §12 原定「钩子只定接口、不加调用点」，触发型在无调用点时是死代码。
    决策：本期在玩家侧加钩子调用点——玩家攻击（`combat_manage.PAE_manage`）、玩家受击（`combat_manage.player_attacted`）；敌人侧的触发型效果本期不做。
    理由：先把玩家身上的触发型做通，改动面小，且不动 `enemy_manage` 的结算流程。
    后果：敌人身上的触发型 buff（敌人受击 / 攻击时触发）本期做不了，敌人侧只能做累加型与周期型；**「施法时」「击杀时」「移动时」「暴击时」这四个时刻 2026-09-14 定案一律不补**，因此心猿意马（施法时 1% 失败）、焚心火（施放技能时每层受伤）、戾气缠身（击杀 +2 层）、业火（按击杀增伤）等依赖这些时刻的效果本期均不落地。
-   **ADR-14【设计预留】动作型效果以「动作指令」返回，由管理类统一执行**（2026-09-14）。
    背景：ADR-9 引入「到点执行动作」的第二条管线后，动作该在 buff 实例里就地执行、还是交给管理类，决定了 `BUFF` 类是否要依赖玩家 / 敌人对象与全局。
    决策：buff 实例只产出「动作指令」（数据），由 `Player_Buff_Manage`（及敌人侧对应管理类）统一执行；与现有 `start_buff()` 产出数据、`updata_end_buff_attr()` 统一处理的方向一致。
    理由：保持单向数据流，`BUFF` 类不反向依赖目标与全局；目标抽象由管理类承担，玩家 / 敌人各自适配。
    后果：管理类成为唯一「知道目标是谁」的层；运行对象的存档内容保持为纯数据（不带方法）；代价是多一层指令对象的转发。
-   **ADR-15【术语决定，非实现】「传统有无型 / 新版叠层型」保留为领域术语，代码上不分家**（2026-09-14）。
    背景：最初设想把 buff 分成两个大类型、「各自处理」，即两套容器两套循环。
    决策：该两分法作为**领域概念**保留，用于数值设计与文档表述；**代码上不分成两套容器或两套循环**——容器共用，累加型走现有 `end_buff_attr` 管线，动作型走 ADR-9 的第二条管线；`stackable` 只是一个字段。
    理由：ADR-8（单计时器）+ ADR-10（通道挂效果行）落地后，两类 buff 在容器、记账、存档、展示四处已无结构差异，分家会把这些全部复制两份。真正的分水岭是「累加 vs 动作」。
    后果：术语与代码不再是同构关系——读代码时看不到「两个大类型」，只在 `stackable` 字段与数值配置上体现；文档需持续说明这一点，避免后来者按术语去找两套实现。
-   **ADR-16【设计预留】净化本期不做，但保留获得流程的拦截点**（2026-09-14）。
    背景：`idea4` L443 明确净化系列是体系级二选一——一旦做，debuff 就全部得走「单层数值低 + 叠层型」，与本稿「单 buff 数值高、以有无为限制」的路线相冲突。
    决策：本期不实装净化；但在「获得规则引擎」（§4.2-1）的流程里**保留第 ② 步「净化抵消」的拦截位置**（空实现）。
    理由：与 §4.2-1 原设计一致；留拦截点则将来实装净化无需改流程骨架，只是填空。
    后果：没有净化类 buff；「将来是否实装净化」仍是未决的体系级二选一（见 §9）。
-   **ADR-17【本期实现】不可叠层 buff 重复获得 = 新实例替换旧实例，但替换前必须先撤销旧实例的全部贡献**（2026-09-14 定，2026-09-20 落地）。
    背景：`idea3.md` L126 定「直接让新 buff 取代旧 buff」，L212 又说「早期设计的 buff 安排成不可叠层，重复获得会刷新时间」，两条互相矛盾。而现有 `Player_buff.js` L296 是 `this[time_type_ch][id] = buff_obj` —— **直接覆盖，没有先撤销旧实例**；旧实例的 `only_start_restore` / `continuous_start_restore` 贡献会永久留在 `end_buff_attr` 里（记账 key 为 `buff_type + '_' + buff_id`，L424），新实例继续往同一 key 累加，**同 id 重复获得时效果会叠加而非替换**。现有调用点恰好都避开了「同 id 连续 set」（`player_energy.js` L211-223 都是先 delete 再 set；全部地点里只有 `Place_other.js` L10 的 `sleep_1` 一个场地 buff，进入 set、离开 delete），所以该缺陷目前不显形。
    决策：不可叠层 buff 重复获得采用**替换**：先执行等价于 `delete_buff()` 的整条撤销（含 `start_data` 取负返还），再构建并 `init()` 新实例；可叠层 buff 则走层数 +1，不替换。
    理由：与 idea3 L126 一致；替换后时间自然回到满，等价于 L212 描述的「刷新」；先撤销再重放可保证净效果正确（含施加参数带来的自定义数值）。
    后果：改动 3（获得规则引擎）必须把「撤销旧实例」作为**所有获得路径的前置步骤**（叠层加层、施加参数覆盖数值同样适用）；现有 8 条 buff 与现有调用点行为不变。
    **【2026-09-20 落地】** 在 `set_buff_attr()` 的替换路径里、构建新实例之前加了一行 `this.delete_buff_attr(id)`，复用既有删除路径完成整条撤销。
    无头用例（`_devtools/buff_check/run_check.mjs` 验收 11）做了变异验证：撤掉这一行后，`sleep_1` 连续 set 两次会让 `GS_rest_flag` 的票数变成 **2**，删一次只返还 1，**标记永久卡在 `true`**；加回后票数保持 1、删除后归 0。
-   **ADR-18【本期实现范围】只做一条「燃烧」测试 buff**（2026-09-14）。
    背景：本会话按计划 §5 的 11 项改动展开，先后确定「本期纳入改动 10 + 改动 11」，随后进一步收缩。
    决策：本期实现范围 = **一条「燃烧」buff + 支撑它的最小运行机制**（层数、层数展示、周期型掉血、测试按钮施加入口），用于验证「叠层」与「掉血」两个机制。本会话定下的其余全部内容（改动 5 / 6 / 8 / 9、钩子调用点、敌人侧 buff、消耗品接通、系列覆盖、抵抗力、净化、record / transform / 触发通道）**本期一概不实现，只做设计预留接口**。
    理由：先把范围收到能完整跑通并验证一条链路的最小切片，避免机制未验证就铺开。
    后果：（1）本稿 §5 的 11 项改动、§7 的 ADR-7 ~ ADR-17 中大部分属于「设计预留」，**不能按已完成理解**，文档须明确区分两类，否则后来者会误判进度；（2）roadmap #1 的验收标准本期只能部分满足（仅叠层与掉血，不含"若干新类型 buff"）；（3）存档点**本期一处都不改**（2026-09-14 定案）：`save_Player_Buff_attr` 存整个对象，`stack` 会被自动写入存档，但 `load_init`（`Player_buff.js` L47-78）只恢复 `buff_have_time` 与 `start_flag` / `start_data`，**不恢复 `stack`**，因此读档后层数会丢——该行为作为**已知限制接受**，不修（见 §13.5）。
-   **ADR-19【设计预留】新增一个全局「buff 调度台」，但 buff 容器不搬家**（2026-09-14）。
    背景：曾设想开发一个专门的 buff 管理类，像 `combat_manage` 之于战斗那样，收集各种由 buff 产生的效果并集中生效。核对后发现该类比**不成立**——`combat_manage` 之所以能当「平台」，靠的是作者在 `global_manage.js` L150-153 写明的性质：「只是负责记录参数进行运算的平台，并没有需要保存的信息」，即**无状态、同帧收集 → 同帧结算、不进存档**；而 buff 容器必须跨帧存活且要进存档（`Player.js` L224），性质不同。但该设想指向的缺口是**真实的**：`Player_Buff_Manage` 看不到其他目标，做不到传播（瘟疫之毒 `idea4` L181）、转化（魔气侵蚀 L517）、区域（瘴气 L198）、跨目标伤害（连锁咒 L498）这类操作。
    决策：**新增一个全局协调类（下称「调度台」），但 buff 容器不搬家。**
    -   容器归属：玩家的仍是 `player.player_buff_manage`，敌人侧将来加在 `place_enemy` 上；调度台**自己不装 buff**。
    -   职责：每帧「收集本帧各目标要产生的动作 → 协调只有它能做的跨目标操作 → 按固定顺序统一生效 → 清空」。
    -   状态：**无状态、不进存档**，与 `combat_manage` 一致。
    -   收集机制：**效果由目标 push 上来**（同 `set_player_next_attack`，`Player_active_skills.js` L428）；**目标列表由调度台向「目标来源」清单拉取**（同 `combat_manage.js` L108 `get_combat_place_enemys()`）。来源清单**可扩展**，以便将来容纳非单位目标（格子区域）。
    -   生效时机：独立阶段，固定在 `run_manage.updata_game_data` 的**玩家常态更新（L58）之后、战斗分支（L64）之前**；每帧都跑，非战斗也跑。
    -   生效顺序：**固定为「玩家优先 → 敌人按格子顺序」**，与 `combat_manage` 先 `PAE_manage` 再 `EAP_manage` 的习惯一致。目标之内按 buff 施加先后。
    -   范围：**只管动作型效果**（伤害 / 触发 / 记录 / 转化）；属性类效果仍走现有 `end_buff_attr` → `restart_end_buff` 管线，不经过调度台。
        **【2026-09-24 修订】** 本条的「属性类效果不经过调度台」被推翻：按用户要求，`restart_end_buff()` 的**分派循环与 5 个生效函数都搬进了 `Buff_manage`**。
        修订后口径 = **累加仍在目标侧、分派与生效在调度台**（详见 §16.5）。
        **【2026-09-24 再修订】** 同日又按用户要求把**获得 / 移除 / 清空（`set_buff` / `delete_buff` / `reset_buff`）**也搬进了 `Buff_manage`，
        并把 17 处调用点改成 `global.get_buff_manage().xxx(P_buff, …)`；ADR-19 里「不改现有调用点」这条理由**已失效**（详见 §16.6）。
        现在调度台的定位是「**buff 增删清空 + 效果分派与落地 + 动作通道**」；留在目标侧的是**容器、实例、计时、到期、每帧产出、累加器、展示、存档**。
        理由：既拿到了跨目标协调能力，又不动容器、不动存档、不改现有 13 个 `set_buff_attr` / `delete_buff_attr` 调用点（`player_energy.js` 8 处、`Place_manage.js` 3 处、`mini_event.js` 2 处）。
        后果：（1）「收集」与「生效」在同一帧内紧挨着，**帧内顺序必须精确定义**（本 ADR 已定顺序）；（2）调度台依赖 `player` / `enemy_manage` 等来源，「目标来源」需要一层薄抽象；（3）**敌人被 DoT 打死时的击杀记账 / 掉落路径未定义**——现有入口 `enemy_death(enemy, main_Attack)`（`combat_manage.js` L274）必须传入一次攻击对象，而 DoT 没有攻击对象；本会话决定**留到做敌人侧 buff 时再谈**（见 §9）；（4）本 ADR 与 ADR-12 **并存但不冲突**：ADR-12（含修订行）讨论的是「玩家与敌人的**运行逻辑**是否共用」，本 ADR 讨论的是「**协调层**放在哪里」，ADR-12 本轮未改动。

## 8. 与消耗品属性更新的接口（专设章）

### 8.1 现成链路

```
消耗品使用 → consumable_manage.get_consumable_use_data(效果行)
   效果行 = 模板 items[id].use_attr ∪ 实例 ex_data.bonus
            （Function.js get_merge_use_attr：get_attr 按 attr_id 相加；其他类型原样透传）
   attr_type ∈ { get_attr(实现), get_formula(实现), get_item(占位), get_buff(占位) }
```

`get_buff` 行现在**只打日志不生效**，注释已写明"buff 系统升级规划于 roadmap #1"。

### 8.2 接通方式（改动 11）

把 `get_buff` 分支改为真正施加：读该效果行 → 调 `set_buff_attr`。

### 8.3 契约（ADR-4：取"施加传参"）

-   消耗品侧写法：`{ attr_type:'get_buff', attr_id:'<buff id>', attr_value/时长 … }`（具体字段命名由实现时定）。
-   buff 侧必须支持**施加时覆盖时长/数值**，并保证四件事：
    1. 运行对象保存本次自定义 `time_value`/`data_value`（覆盖 DB 默认）；
    2. **存档**保存这份自定义值，读档能还原（现在 `load_init` 只恢复 `buff_have_time` 与 `start_flag`/`start_data`）；
    3. 展示显示**实际值**（而不是 DB 原文）；
    4. 明确**同 id 但自定义值不同**的 buff 之间是替换还是并存（现规则是"同 id 新替换旧"——若调味要两碗不同的汤各自持有效果，这条规则需要重新考虑）。

### 8.4 暂时不定的部分

-   菜品/调味/药浴等**生活类 buff 的归属与作用域**（是否走 `life` scope、是否永久、是否数量上限）——本稿只留接口，**留待烹饪需求时再定**。
-   在此期间，菜品"每秒恢复"类效果**继续无法生效**（占位），即时数值类可继续走 `get_attr`。

-   **"哪些属性有人读"的又一次实证**（2026-09-22）：为评估"冰系列能不能真的生效"，把敌人侧的属性读取点盘点了一遍，结果见 §15.5——**敌人移速/防御、玩家生命恢复、玩家脆弱都没有读取点**。与上面那条待办同源：**"某个属性有没有人读"这件事，目前只能靠人肉 grep 确认，没有任何机制保障**。盘点结果已记入 §15.5，供日后接入时对照。
-   **布尔类型（`dispatch:'flag'`）的处理方式不妥，待重议**（2026-09-20 提出）。
    **背景**：buff 的全部产出都汇进 `end_buff_attr` 这个**纯数字累加器**，所以布尔量只能先归一成 ±1，再由累加和反推真假。来源是 idea3 问题 4 的「bool 用 0/±1 表达」（见 §10 附录 A.1），是**有意设计**，不是失误。
    **现状机制**（两处代码）：
    1. `Player_buff.js` 的 `get_true_data()`：`true` → `+1`、`false` → `-1`、数字原样返回；
    2. 同文件 `restart_end_buff()` 的 flag 分支：`now_data > 0` → `true`、`== 0` → `false`、`< 0` → **打一条"浮点数误差"告警并按 false 处理**。
       **问题清单（按严重度）**：
    3. **票数制、没有优先级**：同一个 flag 上多个 buff 的效果是"求和"而非"取优先级"。实测：`1 true + 1 false = 0 → false`（禁止方赢）；`2 true + 1 false = +1 → true`（强制方反过来赢）。即「同一个禁止类 buff 能不能生效，取决于场上同时有几个强制类 buff」。
    4. **`now_data == 0` 与"没有 buff 参与"不可区分**：两者都解成 `false`。今天只因 `GS_rest_flag` 的默认值恰好是 `false`（`Enum_game_flag.js` L25）才没暴露；**默认值为 `true` 的 flag 不能交给 buff 系统管**，否则会被"没有 buff 参与"强行改成 `false`。
    5. **负数是正常态却被当成 bug**：`restart_end_buff()` 那条 `else` 的文案是「由于 js 的浮点数误差…需要给前面的流程添加约束」，但 `1 true + 2 false`、单个 `false` 都是**合法语义**，会命中该分支。
    6. **同 id 重复获得会重复计票** → **2026-09-20 已修**：`set_buff_attr()` 的替换路径先调 `delete_buff_attr(id)` 撤销旧实例（ADR-17；变异验证见该条落地行）。
    7. **`revert:false` 的 flag 行会永久漏票** → **2026-09-20 已拦住**：`check_buff_data()` 第 ③ 条自检告警。
    8. **`flag` 通道只对布尔 flag 成立，却没有任何检查**（**未修**）：若效果行的 `target` 指向一个**非布尔**的游戏标记，累加和推出来的真假会被直接写进去。具体地，`global_flag_manage.set_flag('GS_game_statu', true)` → `Game_status.set_game_status()` 检测到名字是 `GS_game_statu` → `change_GS_game_statu(true)`，**把游戏状态设成 `true`**（`GS_game_statu` 本来是 `'NULL'` / `'combat'` 这类字符串）。另一种写法（`value` 直接写字符串）则过不了 `updata_end_buff_attr()` 的 `typeof obj.data != 'number'` 守卫，被静默跳过。**两种写法都不报错。**
    9. **flag 行声明 `per_layer` 语义不明**（**未修**）：布尔量乘层数没有明确含义（`false × 3 = 0`，负号丢失）。当前靠 `start_buff()` 里"先 `get_true_data` 归一、后乘层数"的顺序规避，但没有自检拦。
       **未决方向（都不定案）**：
    -   是否改成**优先级 / 否决制**（禁止优先，或给 flag 效果行加优先级字段）；
    -   是否显式区分「有 buff 管着这个 flag」与「没人管」；
    -   布尔量要不要继续走 `end_buff_attr` 累加器，还是给 flag 单开一条"直接赋值"的通道；
    -   与 §4.3 的 `behavior` 通道（无法行动 / 锁目标 / 施法失败等**战斗行为类**布尔语义）的边界需要写清楚——按计划那些应由战斗系统读取 buff，而不是写全局 flag；
    -   是否保留「全局开关型」这一唯一推荐用途（休息、挑战中、生活类的"是否处于某环境 / 禁止某操作"）。
        **涉及代码**：`Player_buff.js` 的 `get_true_data()` / `restart_end_buff()` / `updata_end_buff_attr()`；数据侧 `Buff_normal.js` 的 `sleep_1`（唯一使用布尔的行）；消费点 `player_energy.js` L149（`GS_rest_flag` 决定精力恢复是否 100% 效率）；相关枚举 `Enum_game_flag.js`。
        **已落地的部分与现状说明**：ADR-17 的漏票修复、`check_buff_data` 第 ③ 条自检；现状描述见 `docs/SPEC.md` §4.4 的「游戏标记（flag）通道」一节。**在定出新方案之前，未修的 3 / 6 / 7 项保持现状，不再实施。**
-   **属性类叠层 buff 缺"层数 = 属性"的稳态语义**（2026-09-20 提出，**依赖 ADR-2 的全量重算，暂不处理**）。
    **需求场景**：冰系列这类"每层给一个**固定比例属性**"的 buff（如「每层防御 −5%」），期望的是**层数一变属性立刻跟着变**——3 层就是 −15%，减到 2 层就是 −10%。
    **现状为什么不行**（两条路都堵着）：
    1. **`tick + per_layer` 是累加语义，不是稳态**：`start_buff()` 每帧产出 `value × stack × 经过时间`，`updata_end_buff_attr()` 把它**累加**进 `end_buff_attr`。所以它是「每秒按当前层数增长」，跑 10 秒就累计到 `−5 × 层数 × 10`，属性会越跑越歪，不是"当前值 = 层数 × 每层值"。
    2. **`on_apply + per_layer` 在获得时只结算一次**：之后加层/减层都**不会重算**（这条已知限制记在 §13.2 的「层数能力边界」与 §13.5）。所以它只是一个"获得那一刻的快照"。
       **实测证据**：`_devtools/buff_check/run_check.mjs` 的**验收 12**（第 376-421 行）造了一条 `tick + attr + evade_ratio −5 + per_layer + revert:true` 的 3 层 buff，跑出来是：3 层 1 秒累计 −15 → 减到 2 层那一帧**零分发**（正确）→ 2 层再跑 1 秒**只再加 −10**（速率立刻跟着层数走）→ 整条清除**精确归零**。也就是说：**减层路径本身没错**（见下），错的是"用 `tick` 表达稳态属性"这个用法。若要 `tick` 表达稳态，就得在层数变化时把这条效果的历史累计**撤回并重算**。
       **顺带澄清一个容易误判的点**：`end_buff_expire()` 减层时返回**空对象**是**正确的**，不是漏生效。因为 `end_buff_attr` 存的是"历史累加值"，减层改变的是**未来的产出速率**（下一帧 `per_layer` 乘新 `stack`），不产生任何"这一帧要分发的变化"。只有在引入全量重算后，减层那一刻才需要产出"撤回旧层数贡献"的分发。
       **需要什么**：ADR-2 的「**按需全量重算**」——在层数变化（加层/减层/清层）的时刻，从所有存活 buff 重新累加 `end_buff_attr` 并重算 `end_data_attr`，而不是只做增量。ADR-2 已按此点名（见 §7）。
       **影响面（将来要做时）**：`Player_buff.js` 的 `end_buff_expire()`（减层路径要产出撤回）、`set_buff_attr()`（加层路径同理）、`updata_end_buff_attr()` / `restart_end_buff()`（增量 → 全量模式切换），以及 `check_buff_data()` 可能需要新增"哪些组合指望全量重算"的说明。
       **暂不处理的理由**：这是 ADR-2 的整块工作，不是本次"层数 + 燃烧切片"的收尾项；且当前**没有任何属性类叠层 buff**（`burn` 是 `dispatch:'resource'`，累加语义本来就是对的），所以现在不做也不会出错。

### 13.5 已知限制（有意接受）

-   **读档后层数变回初始值**（`load_init` 不恢复 `stack`）。

-   **非战斗状态下烧到 0 血不会死**：`combat_manage` 只在战斗流程里检查 `health_point <= 0`（`EAP_manage` L192-197），非战斗时没有任何地方处理；又因血量无自然恢复（`Player_attributes.js` L95 被注释），血量会停在 0。本期不处理。
-   只有一条 buff，「系列覆盖」「同级共存」等规则没有验证对象。
-   `roadmap.md` #1 的验收标准（「新增**若干**新类型 buff」）本期只能部分满足——仅叠层与掉血。

| 周期伤害                 | 固定值（灼烧 L106）、**当前生命%**（中毒 L173）、最大生命%、**施术者攻击力 5%**（赤炎 L115）、按击杀数成长（业火）                                                                                                       | **公式可配置**，不是单个数字  |
| 触发类                   | 攻击时 1%（催眠 L559/失手 L562/心魔入侵 L455）、施法时 1%（心猿意马 L463）、受击时（触电 L323/反噬 L189）、**击杀时 +2 层**（戾气缠身 L513）、移动时（流血 L565）                                                        | 钩子 + 条件 + 概率 + 后果     |
| 记录/延迟结算            | 血咒 L482、业力反噬 L536、因果缠身 L540、**劫数 L544（层数=行动次数，归零天灾）**                                                                                                                                        | 实例上的记录字段 + 明确结算点 |
| 转化/跨 buff             | 魔气侵蚀 L517、火毒 L132、雷噬 L375、蛊毒                                                                                                                                                                                | 查询 + 替换 + 新增的原子接口  |
| **区域目标**             | **瘴气 L198（作用在距离格子上）**、领域压制 L433                                                                                                                                                                         | 目标不限于单位                |
| 层数机制（**七种并存**） | 刷新+时长衰减（火 L103）、不刷新+结束减层（毒 L171/冰 L252/煞气 L506）、无限+触发清层（催眠 L559）、阈值引爆（雷 L342）、层数=倒计时（劫数 L544）、不可叠加（威压 L421）、高级覆盖低级（火 L102）、无条件共存（毒 L170） | 层数必须是**规则组合**        |
| 抗性/免疫                | 冰封后 10 秒抗性 L280、震慑抗性 L425、抵抗力分阶段、不可抵抗 L265                                                                                                                                                        | 免疫本身也是一种 buff         |
| 作用域                   | 战斗外不生效、战斗外加速消失（idea6 L697-708）、生活类永久                                                                                                                                                               | 每帧按游戏状态决定            |
| 净化                     | 圣洁「按等级消耗层数抵消」L445                                                                                                                                                                                           | 获得流程的拦截点              |

**关键观察**：需求里有 7 种层数规则、5 种伤害公式、5 种触发时刻、4 种结算点。为每种组合写代码会爆炸——**只有「声明式数据 + 通用解释器」装得下。**

### 14.2 五层架构

```
┌─────────────────────────────────────────────┐
│ 5. 目标层  Target：玩家 / 敌人 / 区域         │ ← 让 buff 不绑定玩家
├─────────────────────────────────────────────┤
│ 4. 结算层  调度台：收集 → 协调跨目标 → 生效   │ ← 传播/连锁/区域只有这里能做（ADR-19）
├─────────────────────────────────────────────┤
│ 3. 规则层  获得流程 / 每帧流程 / 到期流程     │ ← 抵抗力·净化·覆盖·叠层·层数规则
├─────────────────────────────────────────────┤
│ 2. 实例层  一目标一容器：BuffInstance         │ ← stack / remain / record / charges / caster
├─────────────────────────────────────────────┤
│ 1. 声明层  buff 是纯数据，含效果行与公式      │ ← 加新 buff = 加数据，不写代码
└─────────────────────────────────────────────┘
```

**实例层字段**（`BuffInstance`，住在目标身上，跨帧存活、随目标存档）：

```js
{
    id,             // buff 的 id
    stack,          // 当前层数
    remain_ms,      // 剩余时间
    record: {},     // 记录型字段：血咒累计伤害、因果池、生死咒记录的生命%
    charges: {},    // 计数型字段：劫数的行动次数、触发次数
    caster: {},     // 施加者信息：赤炎的"施术者 5% 攻击力"要用
}
```

### 14.3 效果行字段字典（两轴模型）

**轴一 `out`（产出什么）**

| 取值      | 含义                                                                    |
| --------- | ----------------------------------------------------------------------- |
| `'value'` | 产出一个**加成值**（如"攻速 −20%"）→ 汇进总对象 `end_buff_attr`         |
| `'act'`   | 产出一个**一次性事件**（如"扣 3 点血"、"触发一次判定"）→ 交给调度台执行 |

**轴二 `when`（什么时候产出）**

| 取值         | 含义                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------- |
| `'tick'`     | 周期性产出（配合 `every` 指定毫秒）                                                                |
| `'on_apply'` | 获得时产出一次                                                                                     |
| `'on_xxx'`   | 钩子时刻：`on_attack` / `on_attacked` / `on_cast` / `on_kill` / `on_move` / `on_action`            |
| `'settle'`   | 结算点产出（配合 `at`）：`expire`（到期）/ `threshold`（层数达阈值）/ `countdown_zero`（计数归零） |

**修饰字段**

| 字段         | 含义                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ |
| `v`          | 基础数值（**不含层数**）                                                                   |
| `formula`    | 怎么把 `v` 换算成实际值（见 14.4）                                                         |
| `per_layer`  | 是否乘以当前层数                                                                           |
| `chance`     | 触发概率（仅钩子型）                                                                       |
| `data_type`  | 改哪个属性（仅 `out:'value'`）                                                             |
| `revert`     | 移除 buff 时是否撤销已加的（仅 `out:'value'`）                                             |
| `act`        | 做什么动作（仅 `out:'act'`）：`damage`/`trigger`/`record`/`release`/`spread`/`grant_buff`… |
| `at`         | 结算点（仅 `when:'settle'`）                                                               |
| `on_trigger` | 触发后附带做什么（如清空某系列层数）                                                       |

**buff 级字段**

| 字段       | 含义                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------ |
| `id`       | 唯一 id（**容器用它当 key**）                                                              |
| `tag`      | `positive` / `negative`                                                                    |
| `duration` | 毫秒，或 `'infinite'`                                                                      |
| `scope`    | `normal` / `combat` / `life`                                                               |
| `effects`  | 效果行数组（可含多条、可混不同轴）                                                         |
| `stack`    | `{ max, time:'refresh'\|'no_refresh', decay, expire:'remove'\|'reduce_layer'\|'trigger' }` |
| `series`   | `{ id, level, cover:'lower'\|'coexist' }`                                                  |

### 14.4 公式表

| 名字               | 含义                     |
| ------------------ | ------------------------ |
| `'fixed'`          | 就是 `v` 本身            |
| `'cur_hp_pct'`     | `v` × 目标**当前**生命值 |
| `'max_hp_pct'`     | `v` × 目标**最大**生命值 |
| `'caster_atk_pct'` | `v` × **施加者**攻击力   |
| `'kill_count'`     | `v` × 施加者击杀数       |

> 加一种新公式 = 加一个函数，**不是加一种 buff**。

### 14.5 四个例子

**例 1：灼烧（`act × tick`）** —— 原文 L106「每秒每层受到一次灼烧伤害」、L103「刷新，每多一层时长衰减」

```js
{
    id: 'scorch',                 // 唯一 id，容器拿它当 key
    tag: 'negative',              // 负面 buff
    series: { id: 'fire', level: 1, cover: 'lower' },  // 火系 1 级；只覆盖等级更低的
    duration: 10000,              // 持续 10 秒
    scope: 'combat',              // 战斗类，战斗外不生效
    stack: {
        max: Infinity,            // 不设层数上限
        time: 'refresh',          // 重复获得：剩余时间刷回满
        decay: 0.75,              // 每多一层，时长 ×0.75
        expire: 'remove',         // 到期：整条删除
    },
    effects: [{
        out: 'act',               // 产出一次性事件
        when: 'tick',             // 周期性
        every: 1000,              // 每 1000 毫秒一次
        act: 'damage',            // 动作：造成伤害
        formula: 'fixed',         // 算法：固定值
        v: 5,                     // 基础值 5（示例数值）
        per_layer: true,          // 乘以层数：3 层 → 15
    }],
}
```

**例 2：中毒（`act × tick` + `cur_hp_pct`）** —— 原文 L173、L171

```js
{
    id: 'poison',
    tag: 'negative',
    series: { id: 'poison', cover: 'coexist' },   // 毒系：无条件共存
    duration: 10000,
    scope: 'combat',
    stack: {
        max: Infinity,
        time: 'no_refresh',       // 重复获得：只加层，时间不动
        expire: 'reduce_layer',   // 到期：减 1 层并重启计时
    },
    effects: [{
        out: 'act', when: 'tick', every: 1000,
        act: 'damage',
        formula: 'cur_hp_pct',    // 基数是"当前生命值"，每帧都不同
        v: 0.001,                 // 0.001 = 0.1%
        per_layer: true,
    }],
}
```

> **为什么必须是 `act` 而不是 `value`**：`cur_hp_pct` 基数每帧在变，塞进属性累加器就是在对不同基数的值求和。走 `act` = 每次独立求值。

**例 3：心猿意马 vs 心魔入侵** —— 原文 L463 / L455

```js
// 心猿意马：施法时每层 1% 失败，触发后不清层
{ out:'act', when:'on_cast', chance:0.01, per_layer:true, act:'skill_fail' }

// 心魔入侵：攻击时每层 1% 转攻击友方，触发后清空 demon 系列层数
{ out:'act', when:'on_attack', chance:0.01, per_layer:true, act:'attack_ally',
  on_trigger:{ clear_series:'demon' } }
```

> 两者除了一行 `on_trigger` **结构完全相同**。按"六类通道"分，它们该算 `event` 还是 `behavior`？`on_trigger` 又算哪类？—— 两轴模型里这不是问题。

**例 4：血咒（钩子 + 结算点）** —— 原文 L482

```js
{
    id: 'blood_curse', tag: 'negative',
    series: { id: 'curse', cover: 'coexist' },
    duration: 15000, scope: 'combat',
    stack: { max: 1 },            // 最大 1 层 = 不可叠加
    effects: [
        { out:'act', when:'on_attacked',   // 时机：受到伤害时
          act:'record', key:'blood',       // 动作：记录（不立即生效）
          ratio:0.2 },                     // 记录这次伤害的 20%
        { out:'act', when:'settle', at:'expire',   // 时机：到期这个结算点
          act:'release', key:'blood' },            // 动作：把记录的值释放出去
    ],
}
```

> **同一 buff 同时用了「钩子」与「结算点」两种时机**。

### 14.6 每帧流程

```js
// ① 各目标的 buff 容器自己推进（每帧都跑，非战斗也跑）
for (每个目标 T) {                          // 玩家 / 敌人 / 区域
    for (每个 buff B of T.buffs) {          // 容器以 id 为 key
        B.remain -= dt;                     // 剩余时间扣掉这一帧
        for (每条效果行 E of B.effects) {
            if (E.when == 'tick' && 到了 E.every)   产出请求(E, B, T);
            if (E.when == 'settle' && 命中 E.at)    产出请求(E, B, T);
        }
        if (B.remain <= 0) {                // 到期
            if (B.stack.expire == 'reduce_layer' && B.stack > 1) { B.stack--; B.重算时间(); }
            else 删除 B;                     // 整条删除
        }
    }
}

// ② 钩子触发时（战斗/技能代码只发通知，不直接调 buff）
emit('on_attack', 上下文)                    // 战斗代码里加一行
    → 扫相关 buff 中 when=='on_attack' 的行 → 判定 chance → 产出请求

// ③ 调度台统一结算（无状态，收完就清）
for (每个请求 R) {
    if (R.out == 'value')  累加进 end_buff_attr[R.data_type];  // ← 与现有实现完全一致
    if (R.out == 'act')    执行动作(R);                         // ← 扣血/触发/记录/转化/传播
}
// 跨目标动作（传播 / 连锁 / 区域）只在这里能做

// ④ 分发
end_buff_attr 的差值 → 属性系统 / 游戏状态                    // ← 与现有实现完全一致
```

### 14.7 规则层：三套流程

| 流程     | 内容                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| **获得** | 抵抗力 → 净化 → 系列覆盖 → 同类叠层/刷新 → 免疫 → 入容器（§4.2-1 原设计）            |
| **每帧** | 推进计时 → 按 `when` 产出请求 → 处理 `expire`                                        |
| **到期** | 按 `stack.expire` 分支：`remove` / `reduce_layer`（减层重启）/ `trigger`（触发后清） |

### 14.8 目标层：区域也是目标

**例 5：瘴气** —— 原文 L198「作用在距离格子上…区域内单位每秒 +1 层中毒，每层独立计时」

```js
// 这条 buff 挂在「区域目标」上，不挂在任何人身上
{
    id: 'miasma', duration: 20000, scope: 'combat',
    stack: { max: 5, time: 'refresh', expire: 'remove' },
    effects: [{
        out: 'act', when: 'tick', every: 1000,
        act: 'grant_buff',        // 动作：给目标施加一个 buff
        buff: 'poison',           // 施加 poison
        stack: 1,                 // 1 层
        to: 'units_in_area',      // 给"区域内单位"
    }],
}
```

区域目标没有血量，但它能**每帧向范围内单位 push「获得请求」**——这就是"目标必须是接口"的原因。

### 14.9 现有四种 `buff_type` 在新模型里的写法

| 现有 `buff_type`              | 新写法                                           | 说明                                      |
| ----------------------------- | ------------------------------------------------ | ----------------------------------------- |
| `continuous_start_no_restore` | `{ out:'value', when:'tick', revert:false }`     | 每帧给加成，移除不撤销                    |
| `continuous_start_restore`    | `{ out:'value', when:'tick', revert:true }`      | 每帧给加成，移除时撤销                    |
| `only_start_no_restore`       | `{ out:'value', when:'on_apply', revert:false }` | 只给一次，不撤销                          |
| `only_start_restore`          | `{ out:'value', when:'on_apply', revert:true }`  | 只给一次，移除时撤销（现有疲劳/精力充沛） |

> **两轴模型能完整覆盖现有实现** —— 这不是推翻，而是把现有做法重新表达一遍。

### 14.10 反模式（不会这么做）

| 反模式                           | 为什么                                               |
| -------------------------------- | ---------------------------------------------------- |
| 为每个 buff 写一个 JS 类/函数    | idea 里有名字的 debuff 已 60+ 个，会爆炸成几百个文件 |
| 把公式塞进 `data_value` 单个数字 | 「当前生命 0.1%」与「最大生命 0.1%」没法共用一个数字 |
| 把 buff 做成玩家专属             | 则毒/火/冰全系列（给敌人上 debuff）都做不了          |
| 让 buff 代码直接调战斗函数       | buff × 战斗会缠成网，改一处崩一片；应走钩子总线      |

### 14.11 落地顺序（若从头做）

1. 目标接口 + 容器 + 单计时器 + 层数（**最小可跑**）
2. 声明式效果行 + 公式表（覆盖 `value` + `tick`）
3. 获得流程规则引擎
4. 到期 / 层数规则
5. 调度台 + 钩子总线（`act` + 钩子）
6. 记录 / 转化
7. 区域目标
8. 存档 / 展示

> 与 §6 的批次不同：这里把「调度台 + 钩子」放到第 5 步，因为它们只有在前面跑通后才需要。

## 15. 目标抽象落地规划：玩家与敌人共用一套 buff 运行逻辑（2026-09-22）

> **性质**：**只做规划，不开发**（2026-09-22 明确）。本节是对 §5-5 / ADR-3 / §14.2 第 5 层「目标层」的**落地细化**，不改动前面任何结论。
> **触发原因**：用户计划按 §14 重构 buff 系统，目标之一是**冰系列**（`idea4` L248-312）；而冰系列是「把敌人变得比较弱小」的 **enemy debuff**，现有系统**只服务玩家**。

### 15.1 诉求与已定决定

**诉求**：buff 在玩家身上和敌人身上，**产生的效果一样**。

| #   | 决定                                                                  | 理由                                                                                           |
| --- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | 敌人侧**复用同一套运行逻辑**，不另建管理类                            | 与 ADR-3 一致；避免两套逻辑分叉                                                                |
| 2   | 给敌人**也建派生属性层**（与玩家同构）                                | 否则"每层降 X%"没有落点；且复用 `math_func.js` 的 `calculate_num_attr`，两边的百分比算法不分叉 |
| 3   | 适配层写进 `js/GameRun/enemy_manage.js` 的 `class place_enemy`（L10） | 用户选定；文件数不变，代价是该类从约 193 行涨到约 300 行                                       |

### 15.2 为什么可行：玩家的绑定面只有 5 个函数

`Player_buff.js`（688 行）里**真正绑定玩家的只有文件尾部 5 个模块级函数**：

| 模块级函数                                                        | 现在写死调谁                                           |
| ----------------------------------------------------------------- | ------------------------------------------------------ |
| `change_data_attr(data_type, end_data)`                           | `player.get_player_attributes().change_data_attr(...)` |
| `updata_end_attr_buff()`                                          | `player.updata_end_attr('buff')`                       |
| `global_set_flag(data_type, end_data)`                            | `global.set_flag(...)`                                 |
| `set_game_speed_num(end_data)` / `set_game_speed_ratio(end_data)` | `global.get_time_manage()...`                          |

外加 `run_game_time_buff()` 里读 `global.get_flag('GS_game_statu')`（1 行）。

**`Player_Buff_Manage` 的内部——`end_buff_attr` / `end_data_attr` / `target_dispatch` / `updata_end_buff_attr` / `restart_end_buff` / 层数 / 计时 / 到期——本来就是目标无关的。** 这是通用化可行的根本依据。

### 15.3 "效果一样"的准确边界

**运行逻辑 100% 通用**；**分发接口按目标能力裁剪**——不是每种 `dispatch` 对敌人都有意义：

| dispatch                              | 敌人能否承接 | 说明                                                        |
| ------------------------------------- | ------------ | ----------------------------------------------------------- |
| `attr`（属性）                        | ✅           | 前提是敌人有派生属性层（决定 2）；复用 `calculate_num_attr` |
| `resource`（血量/魔力/精力）          | ⚠️ 部分      | 敌人只有 `health_point`，魔力/精力不存在，要裁剪            |
| `flag`（游戏标记）                    | ❌ 拒绝      | 一个敌人不该改全局「休息标记」                              |
| `game_speed_num` / `game_speed_ratio` | ❌ 拒绝      | 一个敌人不该改游戏速度                                      |

→ 敌人适配层只实现能承接的 dispatch，其余**打一条清晰日志并跳过**。这条建议在架构里写死，否则会出现"某个敌人的 buff 把全局游戏速度改了"。

### 15.4 现状对照（2026-09-22 核对）

| 能力         | 玩家                                                      | 敌人（`place_enemy`）                                                                                                        |
| ------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 属性载体     | `data_attr`：基础层 + 派生 `end_data_attr` + `true_*`     | `combat_attack_attr` / `combat_defense_attr` / `combat_survival_attr`，**只有一层**（`enemy_manage.js` L35-37 从 DB 深拷贝） |
| 属性汇总入口 | `player.updata_end_attr('buff')`                          | **没有**                                                                                                                     |
| 资源当前值   | `health_point`，经 `change_data_attr` **带钳制**          | `health_point` **裸字段**（`combat_manage.js` L166 直接 `-=`）                                                               |
| 派生计算     | `calculate_num_attr` / `true_defense` / `true_health_max` | **没有**（血条直接读 `combat_survival_attr['health_max']`，L72）                                                             |
| buff 容器    | `player.player_buff_manage`                               | **没有**                                                                                                                     |
| 每帧推进     | `player.run_player_normal()`                              | **没有**（只推进主动技能）                                                                                                   |

### 15.5 ⚠️ 属性读取点盘点（决定"冰系列能不能真的生效"）

**通用运行层只解决"buff 算得对、存得住、到得了期"；"算出来有没有人读"是另一堆工作。** 2026-09-22 盘点结果：

| 冰系列要改的属性         | 有没有"人读" | 位置 / 原因                                                                                           |
| ------------------------ | ------------ | ----------------------------------------------------------------------------------------------------- |
| 敌人**攻速**             | ✅           | `enemy_manage.js` L89 / L92（主动技能间隔）                                                           |
| 敌人**移速**             | ❌           | 距离是 `get_random_enemy_distance(格子位置)` 随机出来的（L398），**与移速无关**                       |
| 敌人**防御**             | ❌           | `combat_manage.js` L162-166：玩家打敌人就是 `health_point -= main_Attack.base_damage`，**防御不参与** |
| 玩家**生命恢复**         | ❌           | 机制本身不存在（`Player_attributes.js` L96 被注释，只恢复精力；见 §13.2）                             |

### 16.9 追加改动：目标来源清单拆成 玩家 / 敌人 / 环境（2026-09-24 同日）

**背景**：用户提出「把 `target_registry` 拆开，变成玩家、敌人、环境，解决来源分类的问题」，并要求先判断是否违背计划。

**判断结论：不违背，反而是 ADR-19 的具体化。** 原文（ADR-19）：

-   L282：「**目标列表由调度台向「目标来源」清单拉取**……来源清单**可扩展**，以便将来容纳**非单位目标（格子区域）**」
-   L284：「生效顺序：**固定为「玩家优先 → 敌人按格子顺序」**」
-   后果（2）：「调度台依赖 `player` / `enemy_manage` 等来源，**「目标来源」需要一层薄抽象**」

三点都指向"拆分来源"，所以本次是**照着计划做**。但有四处必须分清（前两处是真坑）：

| #   | 事项                                      | 结论                                                                                                                                                                                                                                |
| --- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **ADR-19 说的是「拉取」，现状是「登记」** | 两者机制不同。玩家是常驻单例 → **登记型**合适；敌人每帧变（刷出/死亡/离场，见 `get_combat_place_enemys()`）、环境随格子存在 → **拉取型**合适。把两者塞进同一个 `register_target` 数组在模型上就是错的——**这才是"来源分类"的真问题** |
| 2   | **"可扩展"不能被写死**                    | 做成三个写死的数组会让第四类来源（召唤物/陷阱/天气）必须改结构。所以采用**来源抽象**：每个来源自己提供 `get_buff_holders()`，加一类只是加一项                                                                                       |
| 3   | **拆结构 vs 接敌人**                      | 只拆结构、仍只有玩家一个来源 → **不违背 §15.8**（没有第二个目标要验证）；拆了并同时实现敌人/环境 → **违背 §15.8 的"先稳态、后通用化"**，也违背 §15「只做规划，不开发」与 ADR-12 修订行。故本次**只拆结构**                          |
| 4   | **今天没有行为收益**                      | `target_registry` 原本只有 1 个元素，且唯一消费者是界面刷新——这是一笔纯结构投资                                                                                                                                                     |

**实际改法**：

| #   | 改动                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `Buff_manage`：`target_registry` → `player_buff_holders` + `target_sources = [{kind:'player', get_buff_holders}, {kind:'enemy', …→[]}, {kind:'area', …→[]}]`                                                                |
| 2   | `register_target(target)` → **`register_buff_holder(kind, buff_holder)`**，只支持 `'player'`；传其它 kind 打日志忽略                                                                                                        |
| 3   | 新增 `get_all_buff_holders()`（按来源顺序合并）；删掉 `get_targets()`                                                                                                                                                       |
| 4   | **来源返回 buff 容器而不是目标对象**（用户定案）：唯一的消费者是界面刷新，返回容器就不必知道 `get_player_buff_manage()` 这个玩家专属方法名，敌人接入时不用另起名；容器身上有 `target`，将来要按目标能力裁剪 dispatch 时再取 |

| 6   | `_devtools`：两处注册调用改名、注册表操作改用 `player_buff_holders`；新增验收 18b（7 条结构断言，含"三类顺序 = `player,enemy,area`"、"敌人/环境为空"、"不支持登记其它 kind"）。断言数 125 → **132**、51 → **52**            |
